Creation accounting contains no raw source address, user profile, or participant identity. It is an anti-abuse budget shared by clients behind the same source address, not a visible appointment owner. Pending budget entries expire with the corresponding reservation lifetime and are pruned on the next successful state write. The default limit allows a shared network to schedule 64 active events. It cannot provide account-level fairness against a distributed source.

Operator recovery for an interrupted restore: keep the relay stopped and rerun `python3 deploy/state-backup.py restore ARCHIVE` with the intended archive. `.restore-pending` prevents starting a partial restoration. Previous staged files can remain after abrupt process death and should be retained until the intended restoration is confirmed.

Evidence: `server-focused.log`, `server-public-safety.log`, `server-integration.log` (57 checks), `server-final.log` (fresh snapshot, relay protocol suite, 6 state backup tests and 3 operations checks), and `state-backup.log`, and `creation-policy-linux.log`.

Existing deployments with an explicit `LANYWHERE_CREATE_PER_MIN=10` retain that operator setting until it is changed during an authorized deployment. The application package alone cannot change the server limit.

A Docker bind-mount visibility glitch exposed a partially updated stats.js during one attempt. The final checks used a tar-stream snapshot of the actual source so the tested files are immutable and match the host tree. This was a host test setup issue, not shipped JavaScript syntax.
