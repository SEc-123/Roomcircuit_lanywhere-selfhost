# HOS 19.0.1 account wire contract

| Boundary | Published compatibility evidence |
| --- | --- |
| Device authentication | HOS 13.0.0 through 19.0.1 uses v7. Requests are form encoded. The singular device-token endpoint returns one token and a lifetime. The documented HOS 18–19 requests omit User-Agent. The batched JSON interface starts in HOS 20. [NintendoClients DAuth](https://github.com/kinnay/NintendoClients/wiki/DAuth-Server) |
| Application authentication | HOS 19.0.0 through 23.0.1 uses v5. HOS 19 keeps the pre-20 service host and omits User-Agent; the host change and mandatory AAuth TLS client certificate start in HOS 20. The hash-suffixed v2 URL belongs to HOS 5.0–8.1.1. [NintendoClients AAuth](https://github.com/kinnay/NintendoClients/wiki/AAuth-Server#system-versions) |
| BAAS account | The account system module still uses the original service family in HOS 19. The documented account User-Agent identifies SDK and Add-on `19.3.0.0`. The anonymous form token uses `grantType=public_client`, a device assertion and optional `penneId` added in HOS 19. Login/federation can send `naCountry` from HOS 18; `isPersistent` starts in HOS 20. The federation form identifies the identity-provider type and carries the independently verified ID token. [NintendoClients BAAS](https://github.com/kinnay/NintendoClients/wiki/BAAS-Server) |
| Account OAuth | The documented system account client, `NxAccount`, has public client ID `6ffd70c434d303c8` and callback `nintendo://account.nx.sys`. Browser authorization requests `nx`. The token request can ask for specific profile scopes and carry a device authentication token. The documented scope list includes the literal `user.links[].id` field. [NintendoClients Account Server](https://github.com/kinnay/NintendoClients/wiki/Account-Server-(Switch)#methods) |

The Account Server browser and API User-Agent tables end at HOS 15.0.1. The source does not attach a per-build capture to the published NxAccount client pair. The pinned OpenPak implementation describes a PKCE `session_token` intermediary and a query redirect for its `session_token_code` response type; a fragment is used for the `id_token` response type. Verify which browser response type, redirect and account request sequence this exact HOS 19.0.1 build uses. The AAuth v5 documentation uses different names for the media-type field in its description and table. Confirm the title's form rather than broadening its proof requirements. [NintendoClients Account Server headers](https://github.com/kinnay/NintendoClients/wiki/Account-Server-(Switch)#headers) · [OpenPak reference](https://github.com/openpak/nx-baas/blob/cf93fd71d05296ac321a90fa880af707bf35ed44/internal/nxaccount/na.go#L519-L545) · [NintendoClients AAuth v5](https://github.com/kinnay/NintendoClients/wiki/AAuth-Server#version-5)

## Adapter acceptance checks

| Stage | Scope of verification |
| --- | --- |
| DAuth and DCERT | Verify the device proof against an enrolled key, nonce and supported profile. The signed device role publishes its own key at the referenced JWK URL. The independent TLS device proof uses the realm's enrollment policy. Genuine platform-device proof and the console's TLS credential selection require their own authorized device validation. [NintendoClients device token contract](https://github.com/kinnay/NintendoClients/wiki/Switch-Tokens#dauth-tokens) |
| Anonymous BAAS | Ensure the form grants only the known anonymous device role. The scalar reply includes a signed access token, lifetime and token type. The credential uses the anonymous grant-class claim and its own access signing-key reference. Optional Penne metadata does not decide authorization. [NintendoClients BAAS](https://github.com/kinnay/NintendoClients/wiki/BAAS-Server#post-100applicationtoken) · [NintendoClients token roles](https://github.com/kinnay/NintendoClients/wiki/Switch-Tokens#baas-access-tokens) |
| BAAS registration, federation and login | Require the enrolled device for native registration and device login. A provisional login can authorize its own profile routes before linking. Federation proves the account and provider. Admission to a title also requires the linked account and application proof. Use canonical BAAS error envelopes. Production-shaped tests should use separate owned origins for BAAS and NA so both expose their original key paths. [BAAS handlers](https://github.com/kinnay/NintendoClients/wiki/BAAS-Server#methods) · [BAAS errors](https://github.com/kinnay/NintendoClients/wiki/Switch-Error-Codes#account-errors-baas) |
| NA OAuth, profile and refresh | Keep the finite `nx` profile scope expansion limited to the registered console client. Preserve PKCE, state, token roles, subject consistency, revocation, and rotating refresh credentials. An independently recognized device proof can additionally constrain a supplied `device_authentication_token`. The native account flow and the separately registered game authorization flow do not share arbitrary callbacks. [NintendoClients account methods](https://github.com/kinnay/NintendoClients/wiki/Account-Server-(Switch)#methods) |
| CAPI | The local singular and plural membership handlers derive access from a live owned grant and linked user. The public source names the service; the pinned OpenPak tests give the response shapes. HOS 19.0.1 request credentials and order still need a console trace. [NintendoClients server list](https://github.com/kinnay/NintendoClients/wiki/Server-List) · [OpenPak CAPI reference](https://github.com/openpak/nx-baas/blob/cf93fd71d05296ac321a90fa880af707bf35ed44/routes.go#L167-L187) |
| AAuth v5 and title settings | Verify the independent title/device proof, own JWK issuer, returned client settings and stable app metadata. The documented title-device claim is `edi`. Backend app registration does not establish the retail game's content authorization, gamecard proof, authority selection or compatibility. [NintendoClients AAuth v5](https://github.com/kinnay/NintendoClients/wiki/AAuth-Server#version-5) · [NintendoClients application token claims](https://github.com/kinnay/NintendoClients/wiki/Switch-Tokens#aauth-tokens) |

The pinned first-link test explicitly exercises a successful account login before association and verifies each returned media URL. The reference game callback separately rejects an ID credential that has no linked principal. That supports a short provisional profile session bound to the enrolled device, followed by an independently authorized federation. The order of profile reads and updates on HOS 19.0.1 remains to be captured. [OpenPak first-link test](https://github.com/openpak/nx-baas/blob/cf93fd71d05296ac321a90fa880af707bf35ed44/flow_test.go#L27-L97) · [OpenPak game identity filter](https://github.com/openpak/nx-baas/blob/cf93fd71d05296ac321a90fa880af707bf35ed44/internal/gameapi/internal.go#L71-L97)

`testdata/hos19-account-contract.json` records public response shapes and version boundaries. `TestHOS19AnonymousBaaSResponse` exercises the real local adapter's anonymous-token handler and optional notification ID. `TestHOS19OAuthProfileScopeTransition` assigns the published public NxAccount pair to the local test issuer, uses a locally approved account fixture, and runs the real local authorize, PKCE and token handlers. It verifies the finite profile-scope transition, rejects undocumented scopes, and checks optional device proof and cross-device rejection on federation. Tests use local services and their own signers. The result covers the adapter contract, with console enrollment, real title proof and game entry pending.
